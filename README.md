# Проверка требований

Агент проверяет спецификации перед началом реализации. Он выделяет требования с опорой на исходный текст, оценивает каждое из них и сопоставляет требования между собой. Отчёт на русском языке показывает готовность к разработке и тестированию. Веб-приложение и командная строка используют один механизм проверки на TypeScript.

## Запуск с Gemini

Требуется Node.js 22.13 или новее. Если вы используете nvm, выполните `nvm use`, чтобы выбрать Node.js 22.

1. Выполните `npm ci`.
2. Создайте ключ Gemini Developer API. Скопируйте `.env.example` в `.env` и задайте `GEMINI_API_KEY`. Ключ также можно передать через переменную окружения процесса. [Создать ключ в Google AI Studio](https://aistudio.google.com/api-keys)
3. Запустите проверку, указав файл с требованиями.

   ```bash
   npm run review -- ./requirements.md
   ```

Команда создаст `requirements-report.pdf` рядом с исходным файлом. Чтобы выбрать формат или место сохранения, передайте путь к отчёту с расширением `.pdf`, `.md`, `.markdown` или `.txt`. Если файл с именем по умолчанию уже существует, явно укажите путь к новому отчёту.

По умолчанию используется `gemini-4-hydrogen`. Чтобы выбрать другую модель Gemini с поддержкой структурированного вывода, задайте `GEMINI_MODEL`. Перед отправкой спецификации в облако проверьте тарифы, квоты и условия использования API. [Тарифы и квоты моделей](https://aistudio.google.com/docs/pricing#gemini-4-hydrogen) · [Условия использования Google API](https://aistudio.google.com/docs/terms)

### Веб-приложение

С тем же файлом `.env` выполните `HOST=127.0.0.1 npm run dev` и откройте приложение. [localhost:3000](http://localhost:3000)

Выберите файл с требованиями и запустите проверку. В результатах выберите PDF, Markdown или TXT и скачайте отчёт. По умолчанию выбран PDF. После одной проверки можно скачать отчёт в нескольких форматах.

Чтобы проверить сборку для развёртывания, выполните `npm run build`, затем `npm start`. Адрес и порт задаются переменными `HOST` и `PORT`. Документы хранятся в памяти на время проверки. Ключ Gemini используется на сервере.

### Публикация из Google AI Studio

1. Поместите исходники в свой репозиторий GitHub. В Google AI Studio Build выберите **Add files → Import from GitHub** и укажите репозиторий. [Google AI Studio Build](https://aistudio.google.com/apps)
2. В разделе **Settings → Secrets** задайте серверный ключ `GEMINI_API_KEY`. Чтобы выбрать другую модель, добавьте `GEMINI_MODEL`. Для запуска в режиме разработки используется `npm run dev`. Приложение использует порт платформы, если он задан, и порт 3000 по умолчанию.
3. Если нужно ограничить доступ к демонстрации, добавьте в **Secrets** надёжный код `REVIEW_ACCESS_CODE`. Интерфейс запросит его перед началом проверки. Укажите тег или коммит развёрнутой версии в `AGENT_VERSION`, чтобы в отчётах при запуске из экспортированных исходников была указана версия агента.
4. Проверьте публичный пример в режиме **Preview**, скачайте отчёт, затем выберите **Publish**, когда приложение будет готово. Если аккаунт соответствует условиям Starter Tier, публикация доступна без настройки биллинга. Для остальных доступно развёртывание через проект Cloud Run с подключённым биллингом. Развёрнутое приложение расходует квоту настроенного проекта Gemini. [Руководство по AI Studio Build](https://aistudio.google.com/docs/aistudio-build-mode) · [Руководство по публикации](https://aistudio.google.com/docs/aistudio-deploying)

С помощью файла Dockerfile можно собрать то же приложение для Cloud Run. Передавайте секреты при запуске контейнера и настройте время ожидания запроса с учётом всех этапов проверки.

## Локальный запуск без облачного ключа

Запустите локальный сервер Ollama с размером контекста не менее 32 768 токенов и загрузите модель Qwen. Если Ollama уже запущена, укажите размер контекста в настройках приложения. [Быстрый старт Ollama](https://docs.ollama.com/quickstart)

```bash
OLLAMA_NO_CLOUD=1 OLLAMA_CONTEXT_LENGTH=32768 ollama serve
```

Запустите проверку из другого терминала.

```bash
ollama pull qwen3.5:9b
LLM_PROVIDER=local npm run review -- ./requirements.pdf ./reports/review.pdf
```

Чтобы изменить модель или порт, задайте `LOCAL_MODEL` и `LOCAL_BASE_URL`. Совместимый сервер llama.cpp может предоставлять тот же Chat Completions API. В локальном режиме агент принимает HTTP-адреса обратной петли без учётных данных и передаёт извлечённый текст локальной модели. Полная проверка на локальном компьютере может занять несколько минут.

```bash
llama-server --model ./qwen3.5-9b.gguf --alias qwen3.5:9b --ctx-size 32768 --parallel 1 \
  --host 127.0.0.1 --port 11439 --reasoning off --no-context-shift
LLM_PROVIDER=local LOCAL_BASE_URL=http://127.0.0.1:11439/v1 \
  npm run review -- ./requirements.pdf ./reports/review.pdf
```

### Запуск с активным сеансом Codex CLI

Установите актуальную версию Codex CLI и войдите в аккаунт. Задайте `LLM_PROVIDER=codex`, чтобы агент обращался к модели через этот сеанс. Для выбора доступной модели задайте `CODEX_MODEL`. В этом режиме агент отправляет извлечённый текст в OpenAI и расходует квоту аккаунта. На каждом этапе проверки запускается временный процесс Codex CLI в режиме только для чтения. Доступ к оболочке, поиск в интернете, плагины и делегирование отключены.

```bash
LLM_PROVIDER=codex npm run review -- ./requirements.pdf ./reports/review.pdf
```

## Методика проверки

Агент принимает PDF с текстовым слоем, Markdown и текст в UTF-8. Ограничения составляют 10 МиБ на файл, 50 страниц PDF и 48 000 символов извлечённого текста. В ссылках на фрагменты PDF указаны номера страниц и строки извлечённого текста. Перед проверкой сканов распознайте текст с помощью OCR. Если текст доступен только на части страниц PDF, отчёт перечислит страницы без извлечённого текста и учтёт это ограничение при оценке готовности. Для локальной модели лимит входного текста ниже, чтобы в контексте на 32 768 токенов осталось место для ответа. Если документ превышает этот лимит, используйте Gemini.

За паспортом прогона и оглавлением следует сводка. В ней кратко описаны выполнимость требований, готовность к разработке и тестированию, а также главное замечание, если оно есть. Сводка строится на проверенных результатах. В отчёт также входят перечень требований и ссылки на исходный текст для замечаний.

В PDF есть кликабельное оглавление и закладки. В Markdown ссылки в оглавлении ведут к именованным якорям. В TXT оглавление перечисляет разделы обычным текстом. [Якоря Markdown в документации GitHub](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#custom-anchors)

Текст в PDF можно выделять. В файл встраивается шрифт с поддержкой кириллицы, латиницы и технических символов. Лицензия шрифта находится в `assets/fonts`. [DejaVu Sans 2.37](https://github.com/dejavu-fonts/dejavu-fonts/releases/tag/version_2_37)

1. **Перечень требований.** Агент выделяет самостоятельные требования из текста, списков, таблиц и контрактов интерфейсов. Он присваивает им идентификаторы отчёта и сохраняет явные идентификаторы исходника, например `FR-1` и `Ф-1`. Агент копирует цитаты из выбранных фрагментов и проверяет, что в отчёте представлен каждый явно заданный идентификатор.
2. **Проверка отдельных требований.** Агент проверяет необходимость, уместность детализации, однозначность, полноту, атомарность, выполнимость, проверяемость, корректность и соответствие формату и правилам. Замечания ссылаются на исходные фрагменты.
3. **Проверка набора требований.** Отдельным запросом к модели агент сопоставляет разделы всего документа, включая требования к приёмке и интерфейсам. Он выделяет до 12 самых существенных замечаний по полноте, непротиворечивости, выполнимости, границам и ответственности, прослеживаемости, проверяемости, удобству изменений, понятности и приоритетам. Агент отклоняет неизвестные ссылки на исходный текст, подсчитывает замечания и оценивает готовность по проверенным данным.

По требованию организаторов критерии опираются на разделы 5.2.5 и 5.2.6 ISO/IEC/IEEE 29148:2018 и раздел 4.3 IEEE 830-1998. Выполнимость оценивается по сведениям из документа. В отчёте отдельно отмечаются выявленные дефекты, условные риски и вопросы к команде проекта. [ISO/IEC/IEEE 29148:2018](https://www.iso.org/standard/72089.html) · [IEEE 830-1998](https://standards.ieee.org/ieee/830/1222/)

За один запуск агент принимает один документ с требованиями и учитывает ссылки на другие разделы этого документа. Если требования разнесены по нескольким файлам, объедините необходимые материалы в одном документе.

## Тесты и пример организаторов

```bash
npm test
npm run check
npm run build
```

Тесты охватывают разбор документов, проверку цитат и ссылок, полноту анализа, взаимодействие с Gemini, форматы отчёта, сводку и навигацию. В тестах используются заранее заданные ответы модели, поэтому ключ API для них не нужен. Проверку с моделью можно повторить на документе организаторов из указанного коммита. [Исходные требования](https://github.com/BCC-HUB/ai-requirements-validator-task/blob/928c1aa364265426105b69ba7a3444eac11b22db/docs/requirements.md)

```bash
curl -fL 'https://raw.githubusercontent.com/BCC-HUB/ai-requirements-validator-task/928c1aa364265426105b69ba7a3444eac11b22db/docs/requirements.md' \
  -o /tmp/organizer-requirements.md
npm run review -- /tmp/organizer-requirements.md ./reports/organizer-review.md
```

Проверьте, что замечания о расхождениях между разделами ссылаются на оба исходных фрагмента. В примере организаторов обратите внимание на границу месяца, ограничение в одно уведомление после изменения порога и ответы на успешные и ошибочные запросы в контракте REST. Оценки модели и группировка замечаний могут отличаться от запуска к запуску.

## Структура исходников

- В `src/review` находятся извлечение текста из документов, критерии проверки, проверка ответов модели и формирование отчётов.
- В `src/model` находятся подключения к Gemini, локальной модели и активному сеансу Codex CLI.
- `src/cli.ts` запускает проверку файла и сохраняет отчёт из командной строки.
- `src/server.ts`, `src/server` и `web` отвечают за загрузку документов и просмотр отчётов в браузере.
